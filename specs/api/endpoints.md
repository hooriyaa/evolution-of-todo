## User Scenarios & Testing *(mandatory)*

### User Story 1 - View My Tasks (Priority: P1)

As a logged-in user of the Todo App, I want to view all my tasks so that I can manage and prioritize them effectively.

**Why this priority**: This is the basic functionality of a todo application - users need to view their tasks to work with them.

**Independent Test**: The system can be fully tested by having a user with tasks log in and verify that they can see all their tasks but not others' tasks.

**Acceptance Scenarios**:

1. **Given** a user is logged in with valid JWT token, **When** they make a GET request to `/api/{user_id}/tasks`, **Then** they receive a list of only their own tasks
2. **Given** a user is logged in with valid JWT token, **When** they make a GET request to `/api/{user_id}/tasks` with status filter, **Then** they receive only tasks matching that status
3. **Given** a user is logged in with valid JWT token, **When** they make a GET request to `/api/{user_id}/tasks` with sort parameter, **Then** their tasks are returned in the requested order

---

### User Story 2 - Create New Task (Priority: P2)

As a logged-in user of the Todo App, I want to create new tasks so that I can keep track of things I need to do.

**Why this priority**: Creating tasks is fundamental functionality that allows users to add items to their todo list.

**Independent Test**: Can be tested by having a user submit a POST request to create a new task and verifying it appears in their task list.

**Acceptance Scenarios**:

1. **Given** a user is logged in with valid JWT token, **When** they make a POST request to `/api/{user_id}/tasks` with valid task data, **Then** a new task is created and returned
2. **Given** a user is logged in with valid JWT token, **When** they make a POST request with invalid task data, **Then** an appropriate error response is returned

---

### User Story 3 - Update Task Details (Priority: P3)

As a logged-in user of the Todo App, I want to update my tasks so that I can modify their details as needed.

**Why this priority**: Users need to be able to modify existing tasks to keep them up to date with changing requirements.

**Independent Test**: Can be tested by having a user update a task and verifying that the changes are saved and reflected in the system.

**Acceptance Scenarios**:

1. **Given** a user is logged in with valid JWT token and has an existing task, **When** they make a PUT request to `/api/{user_id}/tasks/{task_id}` with updated data, **Then** the task is updated with new details
2. **Given** a user is logged in with valid JWT token and tries to update another user's task, **When** they make a PUT request with mismatched user_id, **Then** they receive a 403 Forbidden response

### Edge Cases

- What happens when a user tries to access another user's tasks using a different user_id in the URL?
- How does the system handle requests with expired JWT tokens?
- What if a user tries to delete a task that doesn't exist?
- What if the JWT token is malformed or missing?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST validate JWT tokens in the `Authorization: Bearer <token>` header for all endpoints
- **FR-002**: System MUST verify that the `user_id` in the URL path matches the `user_id` inside the JWT token for all requests
- **FR-003**: System MUST use the same BETTER_AUTH_SECRET environment variable as the frontend to decode JWT tokens
- **FR-004**: System MUST return 401 Unauthorized if no valid JWT token is provided
- **FR-005**: System MUST return 403 Forbidden if the `user_id` in URL doesn't match the `user_id` in the JWT token
- **FR-006**: System MUST return 404 Not Found if the requested task doesn't exist
- **FR-007**: System MUST support GET `/api/{user_id}/tasks` to fetch all tasks for the specified user
- **FR-008**: System MUST support query parameters `status` (pending/completed) for filtering tasks
- **FR-009**: System MUST support query parameter `sort` (created/title) for sorting tasks
- **FR-010**: System MUST support POST `/api/{user_id}/tasks` to create new tasks with title and description
- **FR-011**: System MUST support GET `/api/{user_id}/tasks/{task_id}` to retrieve details of a specific task
- **FR-012**: System MUST support PUT `/api/{user_id}/tasks/{task_id}` to update task title and description
- **FR-013**: System MUST support DELETE `/api/{user_id}/tasks/{task_id}` to permanently delete a task
- **FR-014**: System MUST support PATCH `/api/{user_id}/tasks/{task_id}/complete` to toggle task completion status
- **FR-015**: System MUST enable CORS configuration to allow requests from the Next.js frontend (port 3000)
- **FR-016**: System MUST create Pydantic schemas that align with SQLModel database entities for proper data validation

### Key Entities *(include if feature involves data)*

- **Task**: An item in a user's todo list with attributes: id, title, description, completed status, created timestamp, updated timestamp
- **User**: An authenticated user with a unique id that owns tasks

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of API requests with valid JWT tokens are processed successfully
- **SC-002**: 100% of requests with mismatched user_id in URL vs JWT token are blocked with 403 Forbidden
- **SC-003**: 100% of requests without valid JWT tokens are rejected with 401 Unauthorized
- **SC-004**: Users can successfully create, read, update, and delete their own tasks
- **SC-005**: All API endpoints respond within 500ms under normal load conditions
- **SC-006**: API endpoint filtering by status and sorting by creation/title works correctly
